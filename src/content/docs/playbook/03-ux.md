## What this step is for

UX is about *what happens and in what order* — not what it looks like yet (that's next). Nail down the screens, the primary flow through them, and the words on screen, so that UI design has something real to give shape to instead of guessing.

**Builds on:** [`02-idea-and-pitch`](../02-idea-and-pitch/)

## Template

Copy this into `docs/03-ux.md`.

```markdown
# 03 · UX

## Core user flow
Walk through the single most important path a user takes, screen by screen,
start to finish. (e.g. Onboarding → Home → Create item → Confirmation)

## Screens

### [Screen Name]
**Purpose:** what this screen is for, in one sentence.

**Primary actions:**
- ...

**Secondary actions:**
- ...

**Core elements:** the UI pieces this screen needs (list, form, cards, etc.)

**States to account for:** empty, loading, success, error

**Design considerations:** anything about accessibility, layout, or platform
conventions worth flagging now.

_(Repeat this block for each key screen — home, core action, settings, and
any auth/onboarding screens.)_

## Navigation model
How do screens connect? (Tabs, stack navigation, single page, modal flows.)

## Key on-screen copy
Only the copy that matters for how the flow reads — not a full content
inventory. Headings, primary button labels, and any error/empty states
that need a specific tone.

| Screen | Element | Text |
|--------|---------|------|
| | | |

## Open UX questions
Anything you're not sure about yet that UI or prototyping should help answer.
(See "Validating the flow" below for free ways to actually get answers.)
```

## LLM prompt

Hand this to your AI tool along with your `02-idea-and-pitch.md`.

```text
You are a senior UX designer. Using the attached pitch, define the UX for
this product.

First, describe the single core user flow end-to-end, screen by screen.

Then, for each screen in that flow (plus essential screens like onboarding,
auth, and settings if they apply), produce:
- Purpose (one sentence)
- Primary actions
- Secondary actions
- Core UI elements needed
- States to account for (empty, loading, success, error)
- Any design considerations worth flagging (accessibility, platform
  conventions, layout constraints)

Finish with:
- A navigation model (tabs / stack / single-page / modal flows — whichever
  fits) and why.
- A short table of the highest-stakes on-screen copy (headings, primary
  button labels, key error/empty states) — not a full content inventory.
- 2-3 open UX questions that the next step (visual design / prototyping)
  should help resolve.

Keep screen descriptions tight — a few bullets each, not paragraphs.
```

## Validating the flow

A flow that makes sense on paper doesn't always make sense to someone seeing it cold. Before moving on to visual design, it's worth cheaply checking the *order and structure* of the flow itself — separately from how it looks, which is what [`05-prototype`](../05-prototype/) is for.

- **[Quant-UX](https://www.quant-ux.com)** — free, open-source: build a quick clickable flow (or import one from Figma), share a link, and get click-tracking, screen recordings, success-rate analytics, and A/B testing on it, all without writing code. Good for checking "do people find the thing" before you've committed to a look.
- **A Reddit testing group** — post the flow (or an early prototype) to a community built for exactly this: **[r/AlphaandBetaUsers](https://www.reddit.com/r/AlphaandBetaUsers/)** (testers actively looking to try new products) or **[r/SideProject](https://www.reddit.com/r/SideProject/)** (broader indie-project feedback). Read the subreddit's self-promotion rules first — both expect a clear description, an honest \[Alpha\]/\[Beta\] flair, and you sticking around to reply to comments rather than dropping a link and leaving.

Either route is optional for a small project — a handful of friends clicking through a prototype and telling you where they got confused works too.
